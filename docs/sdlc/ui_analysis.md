## Screen inventory

1. **Sign-in and recovery entry (REQ-001; visible portion of REQ-002).** **Observed — Image:** On a white page, a centered bordered rectangular panel has a bold “Sign in” heading, stacked “Email address” field with `name@example.com` placeholder and “Password” field with masked `********` placeholder. Beneath password is a blue underlined “Forgot password?” link, then a wide dark rectangular “Sign in” button; muted “No account? Contact your administrator.” text is beneath the button. The screen shows fields for email/password, a recovery entry, sign-in action, and administrator guidance. The visual does **not** establish navigation, actual behavior, authentication success, exact colors, or pixel measurements. **Proposed (inferred, not observed) — Standard; REQ-002:** following the recovery link starts the reset-request flow; no successful sign-in destination is assumed.
2. **Reset request (REQ-002–REQ-005).** **Proposed (inferred, not observed) — Story, Standard:** a server-rendered page accepts an email address, with a named submit action and route back to sign-in. Existing synthetic accounts are distinguished internally only to issue an eligible reset link to the in-memory sink; do not show whether an account exists, a link was sent, or a request limit was reached. The per-account five-requests-in-the-preceding-hour limit is internal, not a public counter. No recovery-page layout is observed.
3. **Generic request response (REQ-003–REQ-005).** **Proposed (inferred, not observed) — Standard:** a confirmation page or stable confirmation state presents an identical public response for otherwise equivalent valid requests for existing, unknown, and at-limit accounts, with a route back to sign-in. The sixth request in a preceding hour issues no additional link, but receives the same public response. Neither sink entries nor existence/throttle/issuance status appear in the response. No confirmation design is observed.
4. **Eligible-link new-password form (REQ-006–REQ-008).** **Proposed (inferred, not observed) — Story, Standard:** for an otherwise valid unused link submitted **before** `issue_time + 30 minutes`, where `issue_time` means when the link was issued, present a new-password field and submit action. Successful completion changes the associated synthetic account password and consumes the link. Do not display token material or sink contents. Password rules and optional confirmation input remain unspecified.
5. **Invalid, expired, or reused link (REQ-006–REQ-007).** **Proposed (inferred, not observed) — Standard:** opening or submitting an ineligible link leads to an actionable non-success state with a route to request another link or return to sign-in. A link submitted **at** `issue_time + 30 minutes` or later is ineligible, as is a consumed link; neither may complete another reset. Do not echo tokens. The choice to share one error presentation is a proposal, not a supplied layout.
6. **Reset success (REQ-008–REQ-010).** **Proposed (inferred, not observed) — Story, Standard:** after a completed password change, show confirmation and a sign-in route without exposing sink internals. Each success must also invalidate **every active session** of that account and record an owner-directed notification for **every successful reset**. A visible success message cannot prove those effects; verify them separately.

## Step-by-step journeys

- **Recovery request (REQ-002–REQ-005):** **Observed — Image:** sign-in visibly provides “Forgot password?”, but its destination is unproven. **Proposed (inferred, not observed) — Story, Standard:** (1) activate it from sign-in; (2) enter an email on reset request and submit; (3) see the same generic response for otherwise equivalent existing, unknown, and at-limit accounts; (4) internally, only accepted existing-account requests below five per preceding hour record a link in the sink; the sixth does not record another link. Public content must not disclose this difference.
- **Successful reset (REQ-006–REQ-010):** **Proposed (inferred, not observed) — Story, Standard:** (1) the account owner opens an unused link while eligible before issue-time expiry; (2) enter a new password on the new-password screen; (3) submit and recheck eligibility; (4) update the account password, consume the link, invalidate every active session, and record an owner notification; (5) show reset success and offer sign-in. This is not a claim of observed screens or a prescribed sign-in success destination.
- **Ineligible link (REQ-006–REQ-007):** **Proposed (inferred, not observed) — Standard:** (1) open or submit a malformed, reused, or expired link, including exactly at `issue_time + 30 minutes`; (2) do **not** update the password or show success; (3) show accessible non-success guidance to request another link or return to sign-in.

## Assumptions and open questions

- **Assumption — Image:** the host-supplied observation describes the sign-in wireframe because the attachment reader supplied a reference rather than pixels. It fixes sign-in hierarchy and copy only; no actual navigation, authentication result, precise color/pixel specification, downstream design, implemented UI, or test result is established.
- **Assumption — Story, Standard; REQ-005, REQ-011–REQ-012:** synthetic accounts and volatile in-memory notifications are exercise-only internals; the public request response cannot reveal issuance or sink details.
- **Assumption — Standard; REQ-007:** `issue_time` is the issuance timestamp; exactly 30 minutes later is ineligible, not the last eligible moment.
- **Open question (non-blocking; REQ-001, REQ-009):** What successful sign-in behavior and session model are expected? Until specified, do not invent a destination; verify all-session invalidation where sessions exist.
- **Open question (non-blocking; REQ-002–REQ-010):** What precise recovery-page wording, layout, and shared styling are desired? Until specified, all recovery screens are proposals and equivalent requests must receive account-independent public responses.
- **Open question (non-blocking; REQ-008):** What new-password rules, if any, and optional confirmation input should be communicated? Do not infer mandatory rules from the sign-in image.
- **Open question (non-blocking; REQ-006–REQ-007):** Should malformed, reused, and expired links share a single public non-success screen, and which recovery actions should it offer?
